# 04 — Buffer the fee-token approve so drift doesn't strand deposit on APPROVE

> *This was generated by AI during triage.*

**Category:** bug

**Decision (maintainer, 2026-07-28):** Option (B), buffered approval, with a small **2% buffer** (`fee * 1.02`) — not option (A) unlimited approval (ruled out by this repo's security doctrine, see below) and not option (C) frozen quote.

**What's broken:** After `APPROVE wstETH` mines successfully for the then-current `feeAmount`, a slightly higher re-quoted fee (a few wei of drift) leaves `needsUnderlyingApproval` (`convertApprovalNeeds`, consumed around `web/components/ActionModal.tsx:606`) true again. The deposit UI falls back to the `APPROVE wstETH` step instead of advancing to `DEPOSIT`, even though the step showed `CONFIRMED` moments earlier. First surfaced in `docs/dogfood-reports/2026-07-28-c1024d9-dogfood.md` (Paper Cuts, yield-cyclist persona, severity: medium) — pre-existing behavior, not introduced by `c1024d9`.

**Why (A) was ruled out:** this repo's `AGENTS.md` requires reading `https://ethskills.com/SKILL.md` (and its linked `security/SKILL.md`) before shipping anything onchain-adjacent. That security guidance is explicit: *"Never use `type(uint256).max` as approval amount"* — unlimited approval maximizes blast radius if the spender contract (the OVRFLO vault or a zap/fee contract) is ever compromised via a proxy bug, governance attack, or undiscovered vulnerability. The dogfood report's own recommendation of (A) directly contradicted this repo's mandated security doctrine and was not implemented.

**Desired behavior:** On `APPROVE wstETH`, approve `feeAmount * 1.02` (2% headroom) instead of the exact quoted `feeAmount`. When the deposit re-quotes the fee immediately before submit, as long as the new quote is still `<= approvedAmount`, `needsUnderlyingApproval` stays false and the UI advances straight to `DEPOSIT` — no second approve prompt. If a re-quote ever exceeds the buffered amount (a bigger swing than 2%, e.g. real market movement rather than block-to-block drift), falling back to `needsUnderlyingApproval = true` and re-prompting `APPROVE wstETH` is correct, expected behavior, not a bug to route around.

**Key interfaces:**
- `convertApprovalNeeds` (consumed around `web/components/ActionModal.tsx:606`) — the underlying-approval branch of its `needsUnderlyingApproval` computation should compare the live re-quoted fee against the *previously approved* amount, not just the current quote, so a live allowance that already covers the re-quote isn't misreported as insufficient
- Whatever constructs the `APPROVE wstETH` transaction's `amount` argument — should submit `feeAmount * 102n / 100n` (or equivalent fixed-point 2% multiplier), not the exact `feeAmount`, and never `type(uint256).max`

**Acceptance criteria:**
- [x] `APPROVE wstETH` submits `feeAmount` scaled by a 2% buffer, not the exact quoted amount and not `type(uint256).max`
- [x] A regression test mines an approve for one fee quote, then re-quotes a fee up to 2% higher, and asserts the deposit step advances directly to `DEPOSIT` with no second approve prompt
- [x] A regression test confirms a re-quote *beyond* the 2% buffer still correctly falls back to requiring a fresh `APPROVE wstETH` (this is intended, not a regression)
- [x] No `type(uint256).max` (or equivalent "infinite") approval anywhere in the frontend fee-approval path

**Out of scope:**
- Any change to the PT-approval path (`needsPtApproval`) — this ticket is scoped to the underlying/fee-token approval only
- Revisiting the 2% figure or the A/B/C tradeoff — both are closed by the maintainer's decision above, not re-litigated per ticket
- Option (C) (frozen quote) — not chosen, no staleness/re-quote-contract work needed

**Blocked by:** None — decision made, ready to implement.
