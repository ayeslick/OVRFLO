The short answer

Feasibility

Yes — and it is unusually close. The app is already a clean static export with a single route, no client-side router, no server runtime, no service worker, and a system font stack with no external CDN. There is no framework work to do. The absolute /-rooted asset paths that break most Next-on-IPFS attempts are only fatal on path-style gateways; on a subdomain gateway, a DNSLink domain, or .eth.link, the existing out/ directory already serves correctly as-is.

The real work is not conversion. It is deciding what you are buying, because three separate things do not come along for the ride.

What does not decentralize with the hosting. Wallet-connected reads route through one baked-in RPC URL with no fallback list. Position discovery routes through the Ponder indexer — and verification found that this is load-bearing in a way the codebase's own graceful-degradation story understates: fetchHeldStreamIds throws when the indexer is unconfigured, the on-chain reads only re-verify IDs the indexer already supplied, and event-scan rediscovery is banned project-wide by check-banned-patterns.sh. There is currently no path by which a user discovers their own streams without the indexer. Publishing the UI bytes to IPFS does not change any of that, and immutability makes remediation heavier than editing an env var and redeploying.

What you actively lose. frame-ancestors, X-Frame-Options, and HSTS cannot be delivered without response headers. Meta-tag CSP carries most directives but the spec excludes frame-ancestors outright, and XFO and HSTS have no meta equivalent at all. The build-csp.mjs / csp-hash-inline.mjs machinery this repo deliberately built — twelve inline-script hashes, no 'unsafe-inline' — simply does not reach a user arriving through a raw gateway. The same commit ships materially different protection depending on which door the user walked through.

What is genuinely worth having. Availability if the host or registrar fails; a user-exit path that survives the team; a verifiable answer to "is this the frontend that was reviewed"; and — the finding five of five ideation frames reached independently — governance over who can repoint the audience at different code. That last one is a gap today, on Vercel, before IPFS enters the picture.

Worth stating plainly

No decentralization, IPFS, ENS, or censorship-resistance goal is recorded anywhere in README.md, STRATEGY.md, CONCEPTS.md, BASE_SECURITY.md, VAULT_SECURITY.md, or the twenty critical patterns. The deploy target of record is "static export on a managed edge host." Proposing IPFS as the primary surface is a strategy change that currently has no written goal behind it. Every idea below is scoped as an addition or an insurance policy rather than a replacement, which is why none of them require that argument to be won first.

Codebase Context

Build
next.config.ts sets output: "export" and images.unoptimized: true. Build chain is wagmi generate → build-csp.mjs → next build → csp-hash-inline.mjs → verify-static-export.mjs. No trailingSlash, basePath, or assetPrefix anywhere.
Routes
app/ holds exactly three files: page.tsx, layout.tsx, opengraph-image.tsx. No dynamic segments. Zero occurrences of useRouter or next/navigation. out/index.html is 13,434 bytes; 404.html and _not-found.html are an identical 11,150-byte pair.
Security headers
CSP generated at build time into both vercel.json and public/_headers (Cloudflare Pages / Netlify format — already shipping in out/), then post-processed to add twelve sha256 inline-script hashes. Also ships XFO DENY, nosniff, Referrer-Policy, Permissions-Policy, and HSTS preload.
Frozen config
Seven NEXT_PUBLIC_* values baked into the bundle: chain id, factory address, RPC URL, Reown project id (falls back to 32 zeros), Ponder URL, Sablier indexer URL, site origin (defaults to https://overflow.finance).
Runtime deps
One RPC transport, http(rpcUrl), no fallback list. Ponder indexer for borrow demand and held-stream discovery. WalletConnect / Reown relays. lib/wagmi.ts:55 reports window.location.origin as session metadata at runtime.
Pipeline
No CI exists — .github/workflows is absent. Any publish automation is greenfield.
Governance
A timelocked multisig owns OVRFLOFactory; all admin operations require consensus plus delay; the factory is the single admin entry point. Nothing equivalent governs the frontend.
External
Fleek hosting shut down Jan 2026; Cloudflare's public IPFS gateway was decommissioned Aug 2024; web3.storage became Storacha and dropped plain pinning. Currently viable: Pinata, Filebase, self-hosted Kubo. Uniswap runs DNSLink-behind-CDN as primary since 2019; Lido applies IPFS only at the staking-widget level.

Topic Axes

  1. Build-output portability — relative vs absolute paths, trailing slash, SPA and 404 fallback, absolute OG image URL, per-CID root assumptions.
  2. Origin-bound security posture — CSP, HSTS, and frame-ancestors delivery without a server; gateway origin isolation; the wallet Verify API and Reown allowlist; what is actually lost or gained.
  3. Runtime backend dependencies — RPC, Ponder indexer, and Reown project id baked into an immutable artifact; what "decentralized frontend" means while these remain centralized chokepoints.
  4. Publish & pointer pipeline — pinning provider, CI, ENS contenthash vs DNSLink vs IPNS, release cadence, CID-to-source verifiability, and who holds the key that can repoint.

1. Two doors, one artifact

Axis 2 · Origin-bound security posture Confidence 90% Complexity Medium
Description

Do not replace the host. Make the CDN serve a DNSLink-pinned CID, so app.overflow.finance keeps every real response header while the byte-identical CID is reachable through .eth.link and public gateways as a declared-degraded second door. One artifact, two delivery paths, and only one of them loses protection.

This choice also deletes most of the anticipated porting work. Absolute /-rooted paths resolve correctly on subdomain gateways, DNSLink domains, and .eth.link — they only break on path-style gateways such as ipfs.io/ipfs/<cid>/. Declaring path gateways out of scope is a one-line stance that removes the entire "make Next portable" workstream, rather than automating it.

The deliverable that makes this real is a written record of what the second door lacks — modeled on docs/audit/rejected-findings-record.md, whose whole purpose is stopping a later reviewer from re-litigating a settled question. "The gateway path ships without frame-ancestors, XFO, and HSTS, deliberately" belongs in that file before someone raises it as a vulnerability.

Basis

direct: next.config.ts:4-7 — "this config intentionally does NOT set security headers. Next's headers() API is a no-op under output: \"export\" — real CSP ships as deploy-target config generated by scripts/build-csp.mjs." public/_headers already exists and carries the full set including frame-ancestors 'none' and HSTS preload.

external: Meta-tag CSP is honored but the spec excludes frame-ancestors, sandbox, and reporting; XFO and HSTS have no meta equivalent. This is what app.uniswap.org has done since 2019 — DNSLink to the current CID behind a CDN, raw gateway accepted as a weaker-header fallback.

Rationale

It is the only framing where nothing currently working gets worse. The CSP investment survives untouched on the path almost every user takes, and the security question narrows from open-ended ("what do we lose on IPFS?") to one answerable sentence about a documented emergency route. Serving the same CID through both doors is what keeps it one artifact to review rather than two frontends to audit.

Downsides

Users who arrive via a raw gateway link genuinely have weaker protection, and you cannot stop people sharing those links. Verification specifically refuted the tempting fix — having the page measure its own headers and disable signing when they are absent — because header presence is not proof of authenticity: a phishing clone serving copied headers would self-certify as trusted while the legitimate degraded copy locked itself down. The honest mechanism is documentation and link hygiene, not a runtime trust gate.

2. Ship the exit page, not the app

Axis 3 · Runtime backend dependencies Confidence 75% Complexity Medium
Description

Reframe the question as the risk behind it: if overflow.finance disappears, can people get their money out? That does not need Next, Tailwind, Reown, or the indexer. The exit surface is a short list of contract calls — claim and unwrap on the vault; repayLoan, closeLoan, withdrawLiquidity, and claimLoanPoolShare on the lending market.

A single hand-written HTML file with inlined viem, an injected-wallet-only connection, and a user-pasted RPC covers it. It has no build step, works on every gateway class including path gateways, needs no CSP headers because it makes no cross-origin requests, and sidesteps the entire Reown origin problem by never constructing an AppKit modal. The two artifacts also have genuinely different lifetimes: the main app changes every sprint, the exit page changes only when the ABI does.

Basis

direct: Verified against src/OVRFLO.sol and src/OVRFLOLending.sol — claim (:429), unwrap (:329), withdrawLiquidity (:334), closeLoan (:457), repayLoan (:487), and claimLoanPoolShare (:590) all exist with the described signatures.

direct: lib/wagmi.ts:52-57 pins Reown metadata to window.location.origin with icons at https://overflow.finance/images/logo.jpeg — a URL fetched by the wallet at connect time, which dies with the domain. An exit page that never constructs AppKit sidesteps this entirely rather than solving it.

external: The ethskills crops skill — already mandated by AGENTS.md — treats user exit as a first-class review criterion, so this answers an obligation the project has already accepted.

Rationale

It is the smallest thing that delivers the actual benefit, and it makes the rest of the IPFS question optional rather than urgent. It also survives every adverse scenario simultaneously — no team, no registrar, no updates, no budget — because it has no build step, no service dependency, and no origin binding. If exactly one idea here gets built, this is the one that changes the risk picture.

Downsides

One real open problem, surfaced by verification rather than assumed away: stream discovery has no on-chain path today. fetchHeldStreamIds throws when the indexer is unconfigured, the chain reads in useHeldStreams only re-verify IDs the indexer supplied, and event-scan rediscovery is banned by check-banned-patterns.sh. An exit page therefore either asks the user to paste stream and loan IDs, or needs a discovery mechanism that does not exist yet — Sablier NFT enumeration is the obvious candidate but needs checking against the deployed contract. This is the piece to scope before committing, not after. Second cost: a hand-written page is a second implementation of transaction construction that can drift from the main app's.

3. One gate, two invariants

Axis 1 · Build-output portability Confidence 88% Complexity Low
Description

Extend the build gate that already exists rather than adding a second one. verify-static-export.mjs fails the build when server-runtime artifacts leak into out/, but asserts nothing about paths or hardcoded origins. Add two checks to that same script: fail on /-rooted URLs outside a commented allowlist, and fail on self-origin residue — absolute https://overflow.finance/... references baked into the shipped bytes.

The residue check matters more than it sounds. Not all residue is equal, and the audit is what tells you which is which: an og:image pointing at a canonical domain is defensible, but lib/wagmi.ts:56's icons: ["https://overflow.finance/images/logo.jpeg"] is fetched by the wallet at connect time and dies with the domain — no CSP and no gateway can rescue it.

Basis

direct: Read scripts/verify-static-export.mjs — it asserts out/ exists and that out/server, out/pages-manifest.json, and out/app-paths-manifest.json are absent, then prints "out/ is clean (no server runtime)." Its own header states the rationale: "so the regression is caught in CI instead of at deploy time" — the identical argument for a path check.

direct: The repo already prefers this shape of enforcement over documentation. check-banned-patterns.sh bans getLogs.*Deposited with a per-pattern error message, and R29/M-17 in build-csp.mjs:102-108 records that missing origins were changed to fail the build because "a deploy could ship a CSP that blocked its own RPC and indexer — silently, because the build stayed green."

Rationale

Roughly fifteen lines in a file that already exists, reusing a gate reviewers already trust rather than introducing a second one they have to learn. It costs nothing if the IPFS question is answered "no," and it is the difference between a port that holds and one that quietly rots as unrelated commits reintroduce origin coupling. Today a green build tells you nothing about which delivery mode actually works.

Downsides

The allowlist needs judgment and will attract argument — someone must decide case by case which absolute references are legitimately canonical. Get that wrong in the strict direction and the gate becomes a nuisance contributors learn to bypass. It also only guards what the build emits; it cannot catch an origin assumption that only manifests at runtime.

4. Govern and attest the pointer

Axis 4 · Publish & pointer pipeline Confidence 80% Complexity Medium
Description

Separate routing from authority. Let DNSLink flip per release so shipping stays fast and cheap — one operator, one DNS edit. Put ovrflo.eth's contenthash under the same timelocked multisig that owns OVRFLOFactory, and treat it as the attestation of record rather than the routing layer. Then have the bundle bake its commit or build number at build time and check itself against the attested pointer through the user's own connected provider, showing green when current, amber when superseded, and red when never attested.

This resolves the timelock's obvious objection: a hotfix still ships in minutes via the fast path, but it ships visibly unattested until consensus catches up — which is the correct incentive rather than a blocker.

Basis

direct: The project's architecture record states the factory is Ownable2Step owned by a timelocked multisig, is "the single admin entry point for all vaults and lending markets," and that "all admin operations require consensus + delay." No equivalent governs the frontend, on any host.

reasoned: A frontend that composes calldata for deposit, createBorrowerLoanPool, and approve is a higher-leverage target than most admin functions, because a swapped spender address drains wallets without touching the contracts at all. The protocol has already decided what governance a high-leverage change deserves; the frontend is exempt only by accident of where it is hosted. Verification's design note is load-bearing here: a bundle cannot contain its own CID, so the client-side check must compare a baked build number, not a CID.

external: CCIP-Read (ERC-3668) offchain and L2 resolvers cut the per-update mainnet cost to near zero after setup, which makes a per-release attestation cadence affordable rather than a quarterly ritual.

Rationale

Five of five ideation frames reached this independently, which is unusual. It is also the finding that pays off whether or not IPFS ever ships: the gap exists today on Vercel. Answer it and the rest of the pipeline design follows; skip it and "decentralized frontend" is a claim with a centralized kill switch behind it.

Downsides

You can no longer hotfix a UI bug through the attested path in five minutes, and that tradeoff deserves to be named explicitly rather than discovered during an incident. Verification also flagged a real gap: on a DNSLink domain the running bundle has no CID in its hostname, so the self-check needs a build-number text record alongside the contenthash — the per-CID subdomain case works cleanly, the DNSLink case needs that extra piece designed. Multisig ceremony per release is real operational weight against a stated preference for minimal machinery.

5. Dark archive with declared trigger events

Axis 4 · Publish & pointer pipeline Confidence 85% Complexity Low
Description

Borrowed from scholarly dark archives such as CLOCKSS and Portico: content is deposited and continuously integrity-checked but deliberately not served, going live only on a pre-defined, publicly documented trigger event. Leave the primary deploy completely unchanged. Publish and dual-pin a CID on every release across two independent providers — Pinata and Filebase — and write a one-page document naming who declares a trigger and what the pointer flip actually is.

Pinning monoculture is the real failure mode here, not IPFS itself. Fleek shut down hosting in January 2026, Cloudflare decommissioned its public gateway in August 2024 and broke Uniswap's links, web3.storage became Storacha and dropped plain pinning, and Infura went enterprise-only. Two independent pinners is the minimum that survives one of them repeating the pattern.

Basis

direct: The deploy target of record is explicit — docs/plans/2026-04-21-001-feat-web-production-readiness-plan.md:41: "UI target = static export on a managed edge host (Vercel/Cloudflare/Netlify)." No decentralization goal appears in any root document or in the twenty critical patterns.

reasoned: Proposing IPFS as primary is therefore a strategy change requiring a documented goal the project does not have. Proposing it as a triggered archive is an insurance policy that changes nothing user-facing and needs no such argument won first. Keeping it dark also avoids the worst outcome of a half-committed deploy — a second production surface real users reach and nobody tests.

Rationale

It is the version of this proposal that survives contact with the project's own written record, costs roughly one CI job, and defers every hard question — headers, Reown allowlist, RPC durability — until a trigger actually fires. Since .github/workflows does not exist yet, this is choosing the first CI pipeline rather than retrofitting one.

Downsides

An archive nobody exercises is an archive nobody knows is broken — this needs a periodic restore drill or it decays into a false sense of security. Two pinning providers means two vendor relationships and two sets of credentials. And it deliberately buys no day-to-day benefit: on any ordinary week, this work is invisible.

6. Settle the origin identity question

Axis 2 · Origin-bound security posture Confidence 82% Complexity Low
Description

Three code paths currently give three different answers to "what origin is this app," and no one chose that. app/layout.tsx:8 bakes a static overflow.finance into metadataBase, so share cards on any mirror claim to be the canonical site. lib/wagmi.ts:55 reports the live window.location.origin to Reown, so the wallet layer correctly exposes wherever the user actually is. lib/wagmi.ts:56 hardcodes an icon URL the wallet fetches from the canonical domain at connect time.

Pick one deliberate policy and make the build enforce it. The consequential half is Reown: project ids use an origin allowlist and the Verify API flags mismatches with wallet-side phishing warnings — and a per-CID subdomain changes on every publish, so it can never be pre-allowlisted. That fact largely decides whether raw CID links are ever user-facing.

Basis

direct: Verified verbatim — app/layout.tsx:8 is const siteOrigin = process.env.NEXT_PUBLIC_SITE_ORIGIN || "https://overflow.finance" feeding metadataBase; lib/wagmi.ts:55 is url: typeof window === "undefined" ? "https://overflow.finance" : window.location.origin.

external: Reown project ids use an origin allowlist, and the Verify API checks the connecting domain cryptographically, flagging mismatches with wallet-side warnings. Hardcoding the metadata url back to the canonical domain is not a fix — it is precisely what a phishing site does.

direct: R29/M-17 in build-csp.mjs:102-108 is the precedent for the enforcement shape: baked-in origin assumptions that can go stale should fail the build loudly rather than ship broken.

Rationale

The same build holding two contradictory self-descriptions reads as suspicious to a security-conscious user, not reassuring. More practically, the Reown constraint is not a one-time migration cost — it is recurring per-deploy friction that desensitizes users to exactly the warning that would matter if a real clone appeared. This codebase has zero tolerance for a CSP origin silently going stale; the Reown allowlist is the same failure shape with no equivalent gate.

Downsides

The honest resolution mostly constrains distribution rather than changing code: keep the primary domain fixed and never put raw CID links in front of users. That is a policy people forget, and it is hard to enforce mechanically. The icon URL fix is trivial (inline a data URI); the metadata policy decision is cheap; the discipline afterwards is the actual cost.

7. Give the frozen RPC a fallback

Axis 3 · Runtime backend dependencies Confidence 78% Complexity Low
Description

lib/wagmi.ts:30-32 configures exactly one transport, http(rpcUrl), with no fallback list. On a mutable host a dead RPC provider is an env-var edit and a redeploy. Pinned to an immutable CID it is permanent: that exact artifact is bricked with no way to patch it. Add fallback([http(rpcUrl), custom(injectedProvider)]) — a user of a wallet dApp definitionally has an EIP-1193 provider — and consider an in-app RPC override field, which per-CID origin isolation actually makes safe to persist.

Basis

direct: lib/wagmi.ts:30-32 — transports: { [mainnet.id]: http(rpcUrl) }, single transport, no fallback. lib/config.ts makes rpcUrl optional, so an unset value silently drops to wagmi's default public transport — a fallback that exists by accident rather than design.

reasoned: Verification confirmed the load-bearing claim: custom(window.ethereum) needs no connect-src grant, because injected-provider calls dispatch into the extension's own process via window.ethereum.request() rather than through fetch or WebSocket from the page's script realm, and CSP's connect-src only governs the latter. The tension worth naming: build-csp.mjs:93-117 pins connect-src to exactly the build-time RPC and indexer origins, so a free-text RPC override and a strict CSP cannot both be absolute — but the wallet-provider half is genuinely CSP-free.

reasoned: The long tail is worse than an outage. Years later, if the RPC domain lapses and is re-registered by someone else, every still-resolvable old CID keeps sending wallet-connected traffic to whatever now sits there. A server redeploy fixes this in minutes; a content-addressed artifact has no fix-in-place.

Rationale

This is where immutability and a centralized chokepoint collide hardest. The indexer already has a degradation story; the RPC is the exception, and it is the one an IPFS deploy cannot quietly fix later. The wallet-provider half is close to one line and needs no CSP change, so the cheap portion of this is nearly free — and it is worth doing on the current host anyway, since rate-limited or revoked keys are an ordinary operational event.

Downsides

Verification narrowed the benefit: custom(window.ethereum) only rescues sessions connected through an injected wallet. WalletConnect-only sessions have no window.ethereum and gain nothing, so this solves less of the durability problem than it first appears. A free-text RPC override has different trust and rate-limit properties and needs the connect-src tension resolved deliberately — probably by relaxing that directive on the gateway build only, which is itself a security decision.
