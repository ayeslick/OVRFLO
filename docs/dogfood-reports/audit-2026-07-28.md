# HIGH

## H-1 · Security · Third-party Sablier withdrawal permanently strands lender funds and bricks pool claims

**Location** `src/OVRFLOLending.sol:603` (`_claimFair`), `:457` (`closeLoan`)

**Issue**
Sablier V2 Lockup's `withdraw(streamId, to, amount)` may be called by **anyone**
so long as `to == recipient`. For a pledged loan stream the recipient is the
OVRFLOLending contract. A third party can therefore push a withdrawal of the
loan's collateral stream into the lending market at any time.

OVRFLOLending tracks recovery through its own counters, not the stream's:

```solidity
uint256 recovered = uint256(loan.drawn) + uint256(loan.repaid);
if (!loan.closed) {
    outstanding  = _outstanding(loan);
    withdrawable = sablier.withdrawableAmountOf(loan.streamId);
    recovered   += uint256(_minUint128(withdrawable, outstanding));
}
uint256 claimable = uint256(contribution) * recovered / totalContributed
    - loanPoolReceived[loanId][account];      // <-- unchecked uint256 subtraction
```

A third-party push decrements `withdrawable` without incrementing `loan.drawn`
or `loanPoolProceeds[loanId]`. Every internal path (`closeLoan`, `_claimFair`'s
harvest) increments `drawn` in lockstep, so this is the only way the two can
diverge — and nothing rejects it.

**Impact**
1. **Bricked claims.** `recovered` falls. For any lender with
   `loanPoolReceived > 0`, `contribution * recovered / totalContributed` drops
   below what they already received and the subtraction reverts with panic
   `0x11`. `claimLoanPoolShare` is dead for that lender until the stream accrues
   past the griefed amount — and permanently once the stream is fully vested.
2. **Permanent fund loss.** The withdrawn ovrfloToken lands in OVRFLOLending but
   is never credited to `loanPoolProceeds`. **OVRFLOLending has no rescue, sweep
   or skim function of any kind** (verified: the only owner functions are
   `setAprBounds`, `setFee`, `setTreasury`). The tokens are unrecoverable by
   anyone, including the multisig. Lenders eat the loss pro-rata.
3. **Bricked loan closure.** `closeLoan` requires
   `withdrawable >= outstanding`. Repeated pushes keep `withdrawable` at zero
   while `outstanding` never falls, so the loan cannot be closed and the
   borrower's stream is never returned.

**Evidence** `_claimFair` uses internal counters; `closeLoan:465` gates on
`withdrawableAmountOf`; Sablier V2 Core `SablierV2Lockup.withdraw` permits any
caller when `to` is the recipient. No sweep function exists in
`src/OVRFLOLending.sol`.

**Reproduction**
1. Borrower creates a loan pool; lenders A and B contribute.
2. Lender A calls `claimLoanPoolShare` once (`loanPoolReceived[A] > 0`).
3. Any address calls
   `sablier.withdraw(loan.streamId, address(lendingMarket), withdrawableAmountOf(streamId))`.
4. Lender A calls `claimLoanPoolShare` again → reverts, panic `0x11`.
5. `closeLoan(loanId)` → reverts `"OVRFLOLending: loan not closable"`.
6. The withdrawn balance sits in the contract with no path out.

**Recommended fix** (two parts, both needed)
- Derive recovery from the stream instead of an internal counter. Replace
  `loan.drawn` reads with `sablier.getWithdrawnAmount(streamId)` minus a
  per-loan baseline snapshotted at pledge time, so third-party pushes are
  automatically accounted into `recovered` and `loanPoolProceeds`.
- Defensively clamp the claim arithmetic so it can never underflow:
  ```solidity
  uint256 entitled = uint256(contribution) * recovered / totalContributed;
  uint256 received = loanPoolReceived[loanId][account];
  uint256 claimable = entitled > received ? entitled - received : 0;
  ```
  (This mirrors `loanPoolClaimable` in `web/lib/lending-math.ts:51`, which
  already clamps correctly — the contract is the one that does not.)

**Confidence** High Confidence (contract logic confirmed by reading; Sablier
permissionless-withdraw behaviour is documented upstream and should be
re-confirmed against the exact deployed bytecode at
`0xAFb979d9afAd1aD27C5eFf4E27226E3AB9e5dCC9` before remediation is signed off).

## H-2 · Security / Reliability · No wrong-network detection anywhere in the UI

**Location** `web/lib/config.ts:19`, `web/lib/wagmi.ts`, every `writeContract`
call site in `web/components/ActionModal.tsx`

**Issue**
`parseChainId` validates `NEXT_PUBLIC_CHAIN_ID` **at build time only**. At
runtime nothing checks the connected wallet's chain:

- No `useChainId`, `useSwitchChain`, or `chainId` argument is used anywhere
  outside `lib/config.ts` (verified by grep across `components/ hooks/ lib/ app/`).
- Reads go through `http(rpcUrl)` pinned to mainnet, so the UI **always renders
  mainnet state** regardless of the wallet's chain.
- Writes go through `useWriteContract` with no `chainId`, so wagmi resolves the
  connector's current chain and broadcasts there.

ETHSKILLS `/frontend-ux` Rule 2 and `/qa` both name this ship-blocking: the flow
must be **Connect Wallet → Switch Network → Approve → Execute**, and "when a user
is on the wrong network, the main action button itself must become a
'Switch to [Chain]' CTA — the header dropdown alone is insufficient." There is no
switch step at any layer here.

**Impact**
A user whose wallet is on Arbitrum/Base/Optimism sees a fully populated,
apparently-live mainnet market table with enabled SUPPLY/BORROW/DEPOSIT buttons.
Signing sends ERC-20 `approve` and protocol calls to mainnet addresses on the
wrong chain. At those addresses on an L2 there is typically no code, so a call
succeeds as a no-op and burns gas while the UI reports the tx confirmed — the
approval silently does nothing, or worse targets an unrelated contract that
happens to occupy the address. Wallet-side simulation is the only thing standing
between the user and this.

**Evidence** `grep -rn "useChainId\|switchChain" web/{components,hooks,lib,app}`
returns only the build-time constant in `lib/config.ts`. `lib/wagmi.ts:19`
pins the read transport to `mainnet.id`.

**Reproduction** Connect a wallet, switch it to any non-mainnet chain from inside
the wallet, reload. The table renders normally; every action button is enabled;
no warning appears.

**Recommended fix** Add a chain gate at the top of the action flow: read
`useConnection().chainId`, and when it differs from `chainId` from
`lib/config.ts`, replace every primary action button's label and handler with
`SWITCH TO ETHEREUM` wired to `useSwitchChain`. Additionally pass
`chainId: MAINNET_CHAIN_ID` to every `writeContract` call so wagmi refuses to
broadcast on the wrong chain even if the gate is bypassed.

*Partial mitigation today:* Reown AppKit is configured with `networks: [mainnet]`
and will usually prompt on connect. That covers the connect moment only, not a
chain switch made afterwards, and does not apply to the injected-connector path.

**Confidence** Confirmed.

## H-3 · Race Condition · Every action button stays live after CONFIRMED — one more click duplicates the transaction

**Location** `web/components/ActionModal.tsx:300` (Supply), `:618` (Convert),
`:488` (SimpleAction), `:927` (Borrow), `:1470` (Repay)

**Issue**
No form's `disabled` predicate includes `actionTx.isConfirmed`, and no form
clears its amount input after a successful transaction. Once the tx confirms,
`busy` drops to `false` and the primary button re-arms with the original
arguments still populated.

```ts
// SupplyForm — after confirmation: busy=false, raw unchanged, amount>0
const disabled =
  !market.lending || aprBps === null || amount === 0n || busy ||
  Boolean(validationError) || matured;
```

The UI simultaneously renders `CONFIRMED` and a `CLOSE` button, so the screen
reads as finished while the live SUPPLY button sits directly above it.

**Impact** Real, duplicated financial state, not just a wasted tx:

| Action | Second click result |
|---|---|
| `supplyLiquidity` | **Second liquidity position created, wallet debited again** |
| `deposit` | **Second PT deposit, second Sablier stream, second fee charged** |
| `wrap` / `unwrap` | **Second conversion, wallet debited again** |
| `repayLoan` | Reverts (`loan closed`) — gas wasted |
| `withdrawLiquidity` / `closeLoan` / `claimLoanPoolShare` | Reverts — gas wasted |
| `createBorrowerLoanPool` | Reverts (stream now escrowed) — gas wasted |

A double-click, an impatient re-click while the confirmation banner renders, or
a mis-tap on mobile is enough. This is the "confirmation-to-cache gap" ETHSKILLS
`/qa` describes, with no `approveCooldown` equivalent on the action leg.

**Evidence** Read the five `disabled` expressions; none references `isConfirmed`.
`web/tests/components/data-layer.test.tsx:138` asserts that CONFIRMED and CLOSE
render on `isConfirmed` — but no test asserts the action button is disabled.

**Reproduction** Open SUPPLY, enter an amount, approve, supply, wait for
`CONFIRMED`, click `SUPPLY @ 10.00%` again → a second `supplyLiquidity` is signed.

**Recommended fix** Add `|| actionTx.isConfirmed` to every form's `disabled`
predicate and clear the amount field in the `isConfirmed` effect. A shared
`terminalState` helper in `useApprovalWriteFlows` would prevent the five call
sites drifting apart again.

**Confidence** Confirmed.

## H-4 · Performance · The landing page issues tens of thousands of eth_calls, and re-issues them after every write

**Location** `web/hooks/useLendingLiquidity.ts:19`, `web/hooks/useLoanBook.ts:23`,
`web/hooks/useBorrowerLoans.ts:16`, `web/lib/invalidate.ts:9`

**Issue**
Every enumeration hook expands `enumerateIds(nextId, 500)` into individual
`useReadContracts` entries:

| Hook | Calls per mount | Mounted by |
|---|---|---|
| `useLendingLiquidity` | up to **500** | `RatesCell` (per market row), `MarketRowDetail`→`PositionList`, `PositionSummaryMarket`, Supply/Borrow/AdjustRate forms |
| `useLoanBook` | up to **2 500** (5 reads × 500 ids) | `PositionSummaryMarket` (per lending market), `PositionList` |
| `useBorrowerLoans` | up to **1 000**, `refetchInterval: 2_000` | `RepayForm` |

`PositionSummary` mounts one `PositionSummaryMarket` per lending market
unconditionally for any connected user (`PositionSummary.tsx:111`). With N
markets that is N × ~3 000 calls on first paint. viem's multicall batches by
calldata size (~1 KB default), so a 2 500-call read fragments into roughly 150+
separate multicall RPC requests, per market.

`invalidateAllOnChainReads` then invalidates the entire `["readContract"]` and
`["readContracts"]` key space after **every** confirmed transaction, re-running
all of it. `useWriteFlow` additionally schedules two more invalidation passes at
2 s and 5 s.

**Impact** Multi-second time-to-interactive; rate-limiting or hard 429s on any
metered RPC provider; a `RepayForm` left open sustains ~1 000 calls every 2
seconds indefinitely. On mobile this is also a battery and data-plan problem.
The cost scales with total protocol history, not with the user's own positions.

**Evidence** The `contracts:` arrays in the three hooks; `refetchInterval: 2_000`
at `useBorrowerLoans.ts:30`; the prefix invalidation at `invalidate.ts:10-12`.

**Recommended fix** Structural — see the architectural list. Short term:
(a) drop `useBorrowerLoans` from `RepayForm` in favour of a single
`loans(loanId)` read for the one loan being repaid, since `action.loanId` is
already known; (b) narrow `invalidateAllOnChainReads` to the contract addresses
actually touched by the transaction.

**Confidence** Confirmed.

## H-5 · Reliability · Positions beyond id 500 are permanently invisible *and* unborrowable

**Location** `web/lib/lending-math.ts:79` (`enumerateIds`), consumed by
`useLendingLiquidity`, `useLoanBook`, `useBorrowerLoans`

**Issue**
```ts
export function enumerateIds(nextId: bigint, maxIds: bigint = MAX_ENUMERATION_IDS) {
  const max = nextId - 1n;
  const capped = max > maxIds ? maxIds : max;   // keeps ids 1..500 — the OLDEST
  ...
}
```
The cap keeps the **oldest** 500 ids, not the newest. Once `nextLiquidityId`
exceeds 501 every subsequently created position is invisible to the client
forever, and the window never advances.

**Impact** This is not merely a display truncation:
- `buildLadder` computes tick depth from the truncated set, so a tick funded
  entirely by post-500 positions shows `total === 0n`.
- `BorrowForm` filters the ladder with `liquidTicks = ladder.filter(t => t.total > 0n)`
  (`ActionModal.tsx:796`), so that tick is **not rendered and cannot be selected**.
- With no selectable tick, `quote`/`gatherLiquidity` never run and BORROW is
  dead — even though `gatherLiquidity` on-chain scans the full id space and
  would find the liquidity.
- Lenders who supplied after position 500 see their capital disappear from
  `PositionSummary` and `PositionList`, and lose the WITHDRAW and ADJUST RATE
  buttons that are the only UI paths to recover it. The funds remain
  contract-recoverable via a direct `withdrawLiquidity` call, but not through
  the app.

`PositionList.tsx:91` shows `SHOWING FIRST 500 — DATA TRUNCATED`, which
communicates a display limitation, not "your position and the withdraw button
are gone."

**Reproduction** Seed a lending market with 501+ liquidity positions; supply from
a fresh account (id 502). The position renders nowhere and the rate it funds is
absent from the borrow ladder.

**Recommended fix** Replace forward id enumeration with event-sourced discovery.
The Ponder indexer is already deployed and already indexes `OVRFLOLending`
(`tools/ponder/ponder.config.ts:49`) — index `LiquiditySupplied` /
`LiquidityWithdrawn` / `BorrowerLoanPoolCreated` and query the user's and the
market's live position ids from it, hydrating only those with on-chain reads.
That fixes H-4 and H-5 together. As an interim stopgap, enumerate the **newest**
500 (`nextId-500 .. nextId-1`) so recent activity is never the part that
vanishes.

**Confidence** Confirmed.

## M-1 · Accessibility · Every amount input is unlabelled

**Location** `web/components/ActionModal.tsx:328`, `:630`, `:1010`, `:1491`;
stream `<select>` at `:955`

```tsx
<input className="input mono" value={raw} onChange={...} placeholder="0.00" />
```

No `<label>`, no `aria-label`, no `aria-labelledby`. `placeholder` is not an
accessible name and disappears on input. The only labelled field in the app is
`SLIPPAGE %` (`:1012`), which proves the pattern was known and not applied. The
stream `<select>` is likewise unlabelled.

Violates **WCAG 2.2 AA 1.3.1 Info and Relationships, 3.3.2 Labels or
Instructions, 4.1.2 Name Role Value**. A screen-reader user reaches the SUPPLY
amount field and hears "edit, blank" with no indication of what is being
entered or in which token.

Additional gaps on the same elements: no `type="text" inputMode="decimal"` (a
mobile user gets an alphabetic keyboard for a numeric field), no
`autoComplete="off"`, no `aria-invalid` when `validationError` is set, and no
`aria-describedby` linking the field to its error text.

`npm run a11y` (axe) does not catch this because it only sweeps the base route —
`scripts/a11y-sweep.sh:34` defines `ROUTES=("$BASE_URL")` and axe never opens a
modal.

**Recommended fix** Give each input a visible `<label htmlFor>` naming the
amount and token (`AMOUNT (wstETH)`), add `inputMode="decimal"`, and wire
`aria-invalid` + `aria-describedby` to the existing error `<div>` (which needs
an `id`). Extend the a11y sweep to open each modal.

**Confidence** Confirmed.

## M-2 · Race Condition · Optimistic approval state survives an on-chain-reverted approval

**Location** `web/hooks/useWriteFlow.ts:24-46`; consumers at
`ActionModal.tsx:275`, `:535`, `:876`, `:1226`, `:1456`

`useWriteFlow` correctly distinguishes a reverted tx from a failed fetch:

```ts
const isConfirmed = receipt.isSuccess && receipt.data?.status === "success";
const isReverted  = receipt.isSuccess && receipt.data?.status === "reverted";
error: write.error ?? receipt.error,   // <-- null on an on-chain revert
```

But every form resets its optimistic approval flag on `error` only:

```ts
useEffect(() => { if (approveTx.error) setApprovedAmount(0n); }, [approveTx.error]);
```

On an on-chain-reverted approval, `error` is `null` and `isReverted` is `true`,
so `approvedAmount` keeps the optimistic value and `approvalCovers` stays true.

**Impact** The UI simultaneously shows `APPROVE: REVERTED ON-CHAIN` and the armed
SUPPLY/DEPOSIT/BORROW button. Clicking it signs an action that must revert on
`transferFrom` — a second wasted gas payment plus a second confusing failure.
All five approve-then-write forms share the defect.

**Recommended fix** Change the guard to
`if (approveTx.error || approveTx.isReverted)` in all five effects — or, better,
expose a single `failed = Boolean(error) || isReverted` from `useWriteFlow` so
the five call sites cannot drift.

**Confidence** Confirmed.

## M-3 · Security (informational asymmetry) · SUPPLY never discloses that liquidity can be consumed as an outright stream purchase

**Location** `web/components/ActionModal.tsx:228` (`SupplyForm`) vs
`src/OVRFLOLending.sol:354` (`sellStreamToLiquidity`)

The contract is explicit: *"The liquidity is consumable as either a sale
(permanent stream transfer via `sellStreamToLiquidity`) or a loan
(stream pledged with obligation); **the lender cannot restrict liquidity to one
path**"* (`OVRFLOLending.sol:302-307`).

The SUPPLY form presents only the lending frame: `SUPPLY RATE`,
`RETURN {lenderReturnBps}`, `WAITING {depth}`, `DEMAND …`. It never states that
a counterparty may instead sell a stream into the position, permanently
transferring the Sablier NFT to the lender in exchange for the full discounted
price. The two outcomes have materially different risk profiles — a loan is
self-repaying with the lender holding a claim; a sale leaves the lender holding
an illiquid stream NFT until maturity.

The entire sale side of the protocol is unreachable from the UI: a grep across
`web/{components,hooks,lib,app}` for `sell|listing|sale|buy` returns **zero**
matches outside the unused `nextSaleListingId` read in `useLending.ts`.
`postSaleListing`, `buyListing`, `cancelSaleListing` and `sellStreamToLiquidity`
are all deployed and callable directly, with no UI, no disclosure and no
positions view for a lender who ends up holding a purchased stream.

**Impact** A lender supplies expecting a self-repaying loan and can instead
receive a stream NFT they have no in-app way to see, value or exit.

**Recommended fix** Add one line of disclosure to the SUPPLY form
(`LIQUIDITY MAY BE FILLED AS A LOAN OR AN OUTRIGHT STREAM PURCHASE`), and surface
purchased streams in `PositionList` — `useHeldStreams` already returns every
stream the user holds, and `isSeriesMatchedStream` already classifies them.

**Confidence** Confirmed.

## M-4 · Accessibility · `RateLadder` radiogroup has no keyboard model

**Location** `web/components/RateLadder.tsx:33-57`

The component uses `role="radiogroup"` with `role="radio"` children and correct
`aria-checked`, but implements none of the required interaction model: no arrow-key
navigation between options, and no roving `tabindex` (all options remain in the
tab order because they are native `<button>`s). A screen-reader user is told
"radio, 1 of 5" and then finds that arrow keys do nothing.

Violates **WCAG 2.2 AA 4.1.2** as applied to the ARIA radiogroup pattern.

**Recommended fix** Either implement the APG radiogroup pattern (Arrow keys move
and select; `tabIndex={selected ? 0 : -1}`), or drop the ARIA roles and use a
native `<fieldset>` + `<input type="radio">` group, which gives the whole
behaviour for free and matches the flat visual treatment.

**Confidence** Confirmed.

## M-5 · Accessibility · Focus trap is escapable, and initial focus is contested

**Location** `web/hooks/useFocusTrap.ts:32`, `web/components/MarketDetail.tsx:26-32`

Two defects:

1. The `keydown` listener is attached to `container`, not `document`. Keyboard
   events only reach it while focus is *inside* the panel. Any route by which
   focus leaves — tabbing out to browser chrome and back, an element being
   removed while focused (which happens constantly here as buttons swap between
   APPROVE/SUPPLY/CLOSE), programmatic focus loss to `<body>` — leaves the trap
   permanently inert, and Tab then walks the page behind the scrim.
2. `useFocusTrap` focuses `focusable[0]` on mount, then `MarketDetail`'s own
   effect focuses the first `<input>`. Two effects competing for initial focus on
   the same commit; which wins depends on effect ordering and on whether the form
   currently renders an input at all (`SimpleActionForm` renders none, so focus
   lands on the modal close button — acceptable, but unintentional).

`ClaimAllModal` compensates by hand (`headingRef.current?.focus()` at
`ClaimAllModal.tsx:122`), which is evidence the base hook is not holding focus
reliably.

**Recommended fix** Attach the `keydown` handler to `document` and check
`container.contains(document.activeElement)`, redirecting focus back into the
panel when it has escaped. Give `useFocusTrap` an optional `initialFocusRef` and
remove `MarketDetail`'s competing effect.

**Confidence** High Confidence.

## M-6 · Race Condition · CLAIM ALL signs a plan frozen at modal-open time

**Location** `web/components/ClaimAllModal.tsx:48`, `:119`

```tsx
const [reviewPlan] = useState<QueuedTx[]>(() => planClaimAll({ pools, streams }));
...
onClick={() => { setStarted(true); queue.start(reviewPlan); ... }}
```

The plan is computed once at mount and never recomputed at confirm. The comment
at `:35` states "nothing signs until CONFIRM QUEUE" — true, but the *plan* is
still the mount-time snapshot. The live `pools`/`streams` props update
underneath it (RESUME correctly re-plans from them at `:132`; START does not).

**Impact** Between opening the modal and clicking CONFIRM QUEUE, a stream can be
claimed in another tab, a loan can be closed permissionlessly by anyone, or a
pool share can be drained. The queue then signs `withdrawMax` on a stream with
nothing withdrawable, or `claimLoanPoolShare` with nothing claimable — both
revert, the queue halts and shows FAILED, and the user must RESUME. Worse in the
multi-tab and slow-network cases the audit brief calls out, and worse still since
`closeLoan` is permissionless so a third party can invalidate the plan.

**Recommended fix** `queue.start(planClaimAll({ pools, streams }))` — the same
call RESUME already makes. One line.

**Confidence** Confirmed.

## M-7 · Race Condition · Signer-switch pause can be beaten by one queued transaction

**Location** `web/hooks/useTxQueue.ts:106-141`

The pause effect (declared first, line 106) and the receipt-advance effect
(declared second, line 119) run in the same commit when a receipt lands on the
render where `user` changed. The pause effect calls `setPaused(true)`, but the
advance effect's closure still holds the pre-update `paused === false`:

```ts
if (paused || nextIndex >= rows.length) { setRunning(false); return; }
execute(rows[nextIndex].tx);          // fires against the NEW signer
```

`execute` reads `userRef.current`, which is already the new address, so a
`withdrawMax(streamId, newUser)` is dispatched for the previous account's stream.

**Impact** Fails closed on-chain — Sablier rejects the withdrawal because
`newUser` is neither recipient nor approved, and `claimLoanPoolShare` reverts
with `not loan pool lender` — so no funds move. But the user gets a wallet
signature prompt they did not initiate, and the queue reports FAILED rather than
the intended `WALLET CHANGED — RE-EVALUATING` (`ClaimAllModal.tsx:100`), sending
them down the wrong recovery path.

**Recommended fix** Track the paused state in a ref alongside the state
(`pausedRef.current = true` inside the pause effect) and read the ref in the
advance effect, or fold both effects into one so the ordering is explicit.

**Confidence** High Confidence.

## M-8 · Security / Availability · Ponder SQL and GraphQL endpoints are publicly exposed with no rate limiting

**Location** `tools/ponder/src/api/index.ts`

```ts
app.use("/sql/*", client({ db, schema }));
app.use("/graphql", graphql({ db, schema }));
```

Both endpoints are mounted unauthenticated with no rate limiting, no query
allowlist, no statement-cost budget and no explicit CORS policy. The browser
bundle points directly at `/sql` via `NEXT_PUBLIC_PONDER_URL`, so the endpoint
must be internet-reachable in production. `@ponder/client` sends arbitrary SQL
text; the app only ever issues two fixed queries (`lib/ponder.ts:47`, `:67`), but
the endpoint accepts anything read-only the schema permits.

**Impact** Availability, primarily. An attacker can issue expensive cross-joins
or unbounded scans against `sablier_streams` × `borrow_events` to exhaust
connections or CPU. When the indexer degrades:
- `useHeldStreams` returns empty → **BORROW shows `NO STREAMS AVAILABLE`** and
  the STREAMS section of `PositionList` shows an error, so users cannot reach the
  borrow or claim-stream flows at all.
- CLAIM ALL loses its stream legs.

Secondarily, it is an unmetered bulk-export surface for the full stream and
borrow graph (addresses, amounts, timings) — public onchain data, but trivially
enumerable in a way the chain is not.

**Recommended fix** Put the indexer behind a reverse proxy with per-IP rate
limiting, a statement timeout and an explicit CORS allowlist for the app origin.
Drop the `/graphql` mount — nothing in `web/` uses it. Best: replace `/sql` with
two purpose-built read endpoints matching the two queries the client actually
issues.

**Confidence** High Confidence (endpoint config confirmed; production deployment
topology not visible from this repo — verify what fronts the indexer).

## M-9 · Security · Indexer data is rendered as position state with no onchain verification

**Location** `web/lib/ponder.ts:62`, `web/hooks/useHeldStreams.ts`,
`web/components/PositionSummary.tsx:86`, `web/components/PositionList.tsx:60`

`fetchHeldStreamIds` returns `recipient`, `sender`, `asset`, `endTime`,
`deposited` and `withdrawn` straight from the indexer. `isSeriesMatchedStream`
filters on indexer-supplied `sender`/`asset`/`endTime` against onchain
`MarketInfo`, and only `withdrawable` is overlaid from a real contract read.

claim reverts — but a user can be shown positions and claimable balances that do
not exist, which is a credible phishing and support-load vector.

**Recommended fix** Treat indexer output as an id-discovery hint only. Hydrate
`recipient`, `deposited` and `withdrawn` from the Sablier contract in the batch
that already reads `withdrawableAmountOf`, and drop any stream whose onchain
recipient is not the connected address.

## M-14 · Reliability · Balance display rounds half-up and can show more than the user holds

## M-15 · Reliability · `gatherLiquidity` is an unbounded loop with O(n) memory allocation

**Location** `src/OVRFLOLending.sol:698`

```solidity
uint256 maxCount = nextLiquidityId - startId;
ids = new uint256[](maxCount);
for (uint256 i = startId; i < nextLiquidityId; i++) { ... }
```

The array is sized to the **entire remaining id space** before any filtering, and
the loop is unbounded. Memory expansion cost is quadratic in `maxCount`.

The UI always passes `startId = 1` (`ActionModal.tsx:855`) and never paginates,
despite the parameter existing precisely for that.

**Impact** As the protocol accumulates liquidity positions, this `eth_call`
approaches and then exceeds the node's `eth_call` gas cap (commonly 50 M). The
`gather` read in `BorrowForm` then errors, `gatherIds` is empty, and the BORROW
button is permanently disabled by `gatherIds.length === 0`. Borrowing dies at a
protocol-history threshold rather than a per-user one, with no warning beforehand.

**Recommended fix** Bound the scan with an explicit `maxScan` parameter and
return the next cursor so the client can page. Size the return array to
`min(maxScan, nextLiquidityId - startId)`. Have `BorrowForm` walk pages until
`sufficient` is true — note it currently discards the `sufficient` return value
entirely (`gatherData?.[1]` is destructured but never read).

**Confidence** High Confidence.

## M-17 · Security · Committed CSP carries dev fallbacks and permits inline script

**Location** `web/vercel.json`, `web/public/_headers`, `web/scripts/build-csp.mjs:61-71`

The committed policy contains the script's *fallback defaults*, not production
origins:

```
connect-src 'self' https://rpc.ankr.com http://localhost:42069 https://api.coingecko.com ...
```

Three problems:
1. **`http://localhost:42069` shipped in a production CSP.** Harmless as an
   allowance (browsers block mixed content anyway) but it is a clear signal these
   files were generated without production env set.
2. **Fail-open on misconfiguration.** If a production build runs without
   `NEXT_PUBLIC_PONDER_URL`/`NEXT_PUBLIC_RPC_URL`, `build-csp.mjs` silently
   substitutes `rpc.ankr.com` and `localhost` rather than failing. The deployed
   app then has a CSP that *blocks its own* indexer and RPC — a silent,
   hard-to-diagnose production outage. The script already fails loudly on an
   invalid URL; it should fail equally loudly on a missing one.
3. **`script-src 'unsafe-inline'`.** This removes most of CSP's XSS value. The
   residual risk is low today (no `dangerouslySetInnerHTML`, no `innerHTML`, no
   `eval`, no user-controlled HTML anywhere — verified by grep) but it means any
   future injection sink is immediately exploitable. `img-src ... https:`
   similarly permits any HTTPS origin as an exfiltration channel.

Also: `https://api.coingecko.com` is allowed but no price API is ever called
(see L-8), and `Permissions-Policy` does not restrict `payment`, `usb` or
`clipboard-read`.

**Recommended fix** Make `build-csp.mjs` exit non-zero when a required
`NEXT_PUBLIC_*` origin is absent and `NODE_ENV=production`. Regenerate and commit
production-origin files, or gitignore them as build artifacts. Replace
`'unsafe-inline'` with hashes for Next's bootstrap scripts. Drop the unused
CoinGecko origin.

**Confidence** Confirmed.

# LOW

**L-1 · Security · Token decimals hardcoded to 18 with no contract-level enforcement.**
`parseAmount` (`ActionModal.tsx:216`) hardcodes `parseUnits(raw, 18)` and
`formatTokenAmount` defaults `decimals = 18`; no `decimals()` read exists
anywhere in `web/`. Pendle PT is 18 by project invariant, but the **underlying**
is not constrained — `grep decimals src/*.sol` returns nothing, so the factory
never enforces an 18-decimal underlying. ETHSKILLS `/security` calls this out
explicitly ("USDC = 6, not 18"). Today's wstETH markets are correct; a
USDC-underlying market would misparse every supply, repay and wrap amount by
10¹². *Fix:* read and thread `decimals()` per token, and enforce
`decimals() == 18` in `setSeriesApproved` if 18 is genuinely an invariant.

`bigintToSafeLength` (`useOvrflos.ts:84`) caps at 100 with no `tooLarge` flag —

mirroring `PositionList.tsx:91`.

# Release recommendation

## Do not ship to mainnet.

Three findings block:

- **H-1** causes **permanent, unrecoverable loss of lender funds** and bricks the
  claim path, triggerable by any address for the cost of gas, with no profit
  motive required and — critically — **no admin recovery path**, because
  OVRFLOLending has no sweep or rescue function. In a protocol whose stated
  security model is "a timelocked multisig can fix things," this is a hole the
  multisig cannot reach.
- **H-2** means a user on the wrong network sees a fully live, apparently-correct
  mainnet UI and signs transactions into the void. Both ETHSKILLS `/frontend-ux`
  and `/qa` classify a missing network gate as ship-blocking, and this app has no
  gate at any layer.
- **H-3** turns one extra click into a duplicated deposit, supply or wrap — real
  duplicated financial state, not a wasted gas payment.

**Ship with known risks** would be defensible for a testnet or invite-only devnet
release once H-2 and H-3 are fixed (both are same-day changes), treating H-1 as a
disclosed, monitored risk with a capped TVL. H-1 must be fixed and re-audited
before any deployment holding real value.

The codebase is otherwise in strong shape and the findings should be read in that
context: typecheck and lint are clean, 313 tests pass, the error-translation
layer is genuinely good (ETHSKILLS Rule 7), the approve/action split is correctly
modelled, on-chain reverts are properly distinguished from RPC failures, and the
stale-liquidity recovery flow is more careful than most production dApps. The
gaps are concentrated in three places: **onchain accounting that trusts internal
counters over external state**, **client-side enumeration that does not scale**,
and **the network/confirmation guards that surround the write path**.
