# OVRFLO Fuzz Properties

> Generated by the Fizz skill against the v1-lite `OVRFLOLending` tick-tree rewrite, consolidated
> from 5 invariant discovery agents (Conservation Auditor, Round-Trip & Rounding Analyst, State
> Transition Mapper, Adversarial Profit Maximizer, Protocol-Type Specialist). Each property is
> described in English and has one of three states:
> - `[ ]` pending — not yet implemented; `/fizz-convert` will pick it up
> - `[x]` implemented — Solidity exists in Properties.sol / handlers
> - `[-]` skipped / manual — `/fizz-convert` will NOT touch it. Use this for TODO stubs,
>   properties that need human judgment, or properties you add yourself later.
>
> Users may freely add their own entries (use any unused `GL-NN` / `SP-NN` ID) and mark
> them `[ ]` to have `/fizz-convert` implement them, or `[-]` to leave them as a spec
> note only.
>
> IDs are stable. Do not renumber.
>
> **This file replaces the pre-rewrite sale-path suite wholesale.** The prior content described
> `offer`/`saleListing`/`createBorrowPool` machinery that no longer exists after the v1-lite
> tick-tree rewrite (`OVRFLOLending` now has exactly two entrypoint families: lender lifecycle
> `supply`/`withdraw`, and borrower lifecycle `borrow`/`repay`/`close`/`claim`, over a permanent
> per-`(market, aprBps, epoch)` coordinate tape). The `GL-NN`/`SP-NN` ID scheme, the
> Scope/Category/Guarantee/Priority structure, and the section layout are preserved from that
> file; the content is not.
>
> **Guarantee tag.** Every property is tagged `SHOULD-HOLD` or `EXPLORATORY`:
> - `SHOULD-HOLD` — explicitly guaranteed by docs/spec/standard or an exact identity
>   (evidence cited inline). If the campaign violates it, that is a **confirmed bug**.
> - `EXPLORATORY` — inferred, not explicitly promised. A violation is a **lead flagged
>   for human review**, not an automatic bug.
>
> This tag is set at generation time so violations can be triaged without post-hoc
> severity guessing. If you edit a property's logic such that it is no longer guaranteed,
> change its tag to `EXPLORATORY`.

- **Scope**: GLOBAL = checked after every handler call (`property_` prefix, public); SPECIFIC = checked at end of relevant handler (internal).
- **Category**: VALID_STATE, STATE_TRANSITION, VARIABLE_TRANSITION, HIGH_LEVEL.
- **Guarantee**: SHOULD-HOLD (documented/spec/standard with evidence) or EXPLORATORY (inferred from code/patterns).
- **Priority**: HIGH, MEDIUM, LOW.

## Global Properties

### Conservation & Solvency

- [x] **GL-01** The lending market's ovrfloToken pot equals, over every loan, `(drawn + repaid)` minus the cumulative amount ever paid out across every `(loan, position)` claim pair, computed WITHOUT reading the `proceeds` mapping (independent cross-check of `proceeds` bookkeeping). HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: algebraic consequence of I-4 composed with I-5; ovrfloToken enters only via `repay`'s pull and `close`/`claim`'s harvest (both credited 1:1 to drawn/repaid) and leaves only via `claim`'s payout. Sources: CON-01.
- [x] **GL-02** `underlying.balanceOf(lending)` equals the sum, over EVERY position ever created (not just live-tick depth), of that position's currently-unfilled amount from `positionState`. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: I-3 — a prefix-sum tree's leaves partition its root by construction, so `Σ_positions unfilled` telescopes to the same quantity I-3 states from the tree side. **Implementer warning: summing only live epochs would undercount — dead/cursor-skipped epochs legitimately hold nonzero sub-atom dust.** Sources: CON-02.
- [x] **GL-03** Independent tree-side cross-check of GL-02: the sum, over every `(market, aprBps, epoch)` tuple ever supplied to, of `(tree.root() − filled) × UNIT`, never exceeds `underlying.balanceOf(lending)`. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: the textbook L-01 solvency mapping, computed independently of GL-02's position-side view — a divergence between the two localizes a bug to the tree layer vs. the position-enumeration layer. Sources: SPEC-08.
- [x] **GL-04** Backstop: `underlying.balanceOf(lending)` equals cumulative supplied minus refunded minus borrowed-out (net of fee), tracked by handler-side ghosts from realized balance deltas rather than on-chain enumeration. HIGH_LEVEL, SHOULD-HOLD, MEDIUM. Evidence: independent of GL-02/GL-03's view-based paths; a GL-02/03 pass with a GL-04 fail (or vice versa) pinpoints whether a bug is in the tree/position layer or the actor-facing payout layer. Sources: CON-03.
- [x] **GL-05** For every `(market, aprBps, epoch)` with both tracked positions and tracked loans, the sum of position-side "filled history" equals the sum of loan-side interval lengths. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: I-1 (tiling) composed with E-1 — `withdraw`'s clamp and `_fillTick`'s bookkeeping are two independently written paths claiming to track the same `filled` coordinate; a bug introduced in only one write site surfaces here even when each side is locally self-consistent. Sources: CON-04.
- [x] **GL-06** For `underlying` and `ptToken` (fixed supply after setup), the sum of every known holder's balance equals `totalSupply()`. `ovrfloToken` is deliberately excluded — it is genuinely minted/burned by vault deposit/wrap/unwrap/claim. HIGH_LEVEL, SHOULD-HOLD, MEDIUM. Evidence: ERC-20 standard; coarse net that catches an entire bug class the identity-based properties above would not — a handler accidentally calling `deal`, a stray mint/burn, or a harness wiring bug letting a balance appear from nowhere. Sources: CON-08.
- [x] **GL-07** Vault combined solvency: `ovrfloToken.totalSupply() ≤ underlying.balanceOf(vault) + ptToken.balanceOf(vault)`, always, regardless of who holds the ovrfloToken. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: the documented combined-solvency form (2026-07-01 fuzz campaign); individual per-leg forms are too strict post-maturity given cross-exit fungibility. Distinctly valuable in THIS suite — unlike vault-only forge suites, this campaign deploys vault + lending + factory together, so a lending-side ovrfloToken flow (claim payout, repay pull) desyncing vault backing is only observable here. Sources: SPEC-01.
- [x] **GL-08** An open loan's pledged stream is always owned by `address(lending)` — never dual-owned, orphaned, or third-party held; and no two simultaneously-open tracked loans ever share the same `streamId`. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: `borrow` NatSpec — a stream already backing an open loan is owned by the lending contract, so a second pledge fails ERC-721's owner check inside Sablier's `transferFrom`; this is also the mechanical basis for why `close`'s cover-check alone is sufficient collateral logic. Sources: SPEC-06, ADV-01.

### Liveness, Donation Resistance & Access Control

- [x] **GL-09** `wrappedUnderlying ≤ underlying.balanceOf(vault)` — a direct donation bypassing `wrap()` can inflate the raw balance but must never let `unwrap` pay out more than the reserve backs. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: wrap/unwrap delta-pair identity; the attack shape is reserve-vs-balance decoupling, not first-depositor share dilution (impossible with 1:1 mint/burn). Sources: SPEC-02.
- [x] **GL-10** A direct underlying donation to the lending contract (bypassing `supply`) cannot increase any tracked position's `positionState().unfilled` amount. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: `positionState` derives entirely from TickTree leaf/prefix state, never from `underlying.balanceOf(address(this))`. Sources: ADV-05.
- [x] **GL-11** A direct ovrfloToken donation to the lending contract (bypassing `repay`/`close`/`claim`) cannot increase any tracked loan's `proceeds[loanId]`. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: `proceeds` is credited only by `repay`, `close`, and `claim`'s just-in-time harvest — never balance-derived. Sources: ADV-04.
- [x] **GL-12** `advanceEpochCursor`'s new `oldestLiveEpoch` never skips an epoch whose available depth is at or above `MIN_LIQUIDITY_AMOUNT` — it stops at `currentEpoch` or at the first epoch failing the dead-epoch predicate. VALID_STATE, SHOULD-HOLD, LOW. Evidence: the advance loop's break condition is checked before every step; a loosened predicate could permanently strand a live epoch's liquidity behind an advanced cursor with no way back (the cursor only moves forward). Sources: ADV-06.
- [x] **GL-13** A non-owner cannot call any lending admin function (`setAprBounds`, `setTickSpacing`, `setFee`, `setTreasury`); storage is unchanged on the revert. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: `OVRFLOLending is Ownable2Step`; every admin function uses `onlyOwner`. `setAprBounds`/`setFee` directly control every future borrower's economics — a bypass would let an attacker reprice the entire book. Sources: ADV-09.
- [x] **GL-14** No admin action (`setAprBounds`) and no later market state retroactively changes an already-originated loan's `aprBps`, interval, or `obligation`. VARIABLE_TRANSITION, SHOULD-HOLD, MEDIUM. Evidence: with no LTV or interest index to re-derive, the domain-equivalent guarantee is "a lender's fixed payout, once locked in, cannot move under later admin rate changes" — the x-ray's "lenders get a fixed, known payout" promise made falsifiable. Sources: SPEC-05.

### Entity Bookkeeping / Slot Existence

- [x] **GL-15** `positions[id].lender != 0` exactly for `id < nextPositionId`. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: append-only allocation, single write site. Sources: VS-01.
- [x] **GL-16** `loans[id].borrower != 0` exactly for `id < nextLoanId`. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: append-only allocation, single write site. Sources: VS-02.
- [x] **GL-17** An unconfigured market (`tickSpacing[market] == 0`) can hold no position or loan. VALID_STATE, SHOULD-HOLD, LOW. Evidence: `_validateTick` reverts `SpacingUnset` before any position/loan write is reachable. Sources: VS-05.
- [x] **GL-18** `loanAt[market][aprBps][epoch][seq] != 0` exactly for `seq < epoch.loanCount`. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: the structural half of loan-list soundness — `loansOf`'s binary search and its scan bound both assume this exactly; a gap corrupts claim discovery silently, no revert, just wrong results. Sources: VS-06.
- [x] **GL-19** `lenderPositionAt[lender]` is exactly (both complete and correct) the set of that lender's positions; `borrowerLoanAt[borrower]` is exactly the set of that borrower's loans. VALID_STATE, SHOULD-HOLD, LOW. Evidence: append-only single write sites for both mappings. Operationally load-bearing, not just correctness-flavored: these indexes are the handlers' only discovery mechanism for an actor's own positions/loans — a desync would silently stop withdraw/claim/repay handlers reaching real entities, deflating campaign coverage with no visible failure. Sources: CON-06, CON-07, VS-03, VS-04.

### Monotonicity

- [x] **GL-20** Per-epoch `filled` is non-decreasing and never exceeds `tree.root()`. VARIABLE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: an underflow in `root() − filled` would permanently DoS every later depth read for that tick — catching the direction violation before the underflow masks it is valuable. Sources: VT-01.
- [x] **GL-21** `loan.drawn`, `loan.repaid`, and `received[loanId][positionId]` are each non-decreasing. VARIABLE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: all three are additive-only in the source (`repay`, `close`, `claim` all only ever add to them). Sources: VT-02, VT-03, VT-04.
- [x] **GL-22** `nextPositionId` and `nextLoanId` are each strictly increasing. VARIABLE_TRANSITION, SHOULD-HOLD, LOW. Evidence: `positionId = nextPositionId++`, `loanId = nextLoanId++`. Sources: VT-05, VT-06.
- [x] **GL-23** Per-tree `leaves`, tree `height`, and per-epoch `loanCount` are each non-decreasing. VARIABLE_TRANSITION, SHOULD-HOLD, MEDIUM. Evidence: append-only growth in `TickTree.append`/`_grow`; `loanCount` increments only in `_fillTick`. Sources: VT-07, VT-10, VT-11.
- [x] **GL-24** `tick.currentEpoch` is non-decreasing; `tick.oldestLiveEpoch` is non-decreasing and always `≤ currentEpoch`. VARIABLE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: if the cursor ever passed `currentEpoch`, every borrow on that tick would read a nonexistent epoch and revert `EmptyTick` forever — a tick-wide DoS with no recovery. Sources: VT-08, VT-09.
- [x] **GL-25** A position's consumed portion (`filledHistory`) never decreases. VARIABLE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: E-1's foundational lemma, derivable from `positionState` alone: `filledHistory = (intervalEnd − intervalStart) − unfilled`. Sources: VT-12.

### State Transitions

- [x] **GL-26** `loan.closed` is a one-way latch — later repay/close attempts on an already-closed loan revert; it never transitions `true → false`. STATE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: no code path clears `closed` once set; both `repay`'s full-repay branch and `close` only ever set it, never clear it. Sources: ST-08.
- [x] **GL-27** `claim` is NOT gated by `loan.closed` (it checks only `loan.borrower != 0`), but `loan.drawn` never moves once `closed == true`. **This asymmetry is intentional — the property must not "fix" it.** VALID_STATE, SHOULD-HOLD, HIGH. Evidence: `claim` routes through neither `_liveLoan` nor any closed-check; "helpfully" adding one would strand co-lenders' unpaid pro-rata share forever, since `claim` is the only remaining exit for proceeds after `close`. Sources: ST-09.
- [x] **GL-28** `tick.currentEpoch` advances by exactly 1, and ONLY at terminal capacity (`tree.height == MAX_HEIGHT && tree.atCapacity()`). STATE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: `_epochAtCapacity` targets the rollover predicate directly; checking `atCapacity()` alone without the height gate would roll an epoch prematurely mid-growth, splitting one continuous tape into two and breaking attribution for every position near the boundary. Sources: ST-13.
- [x] **GL-29** Every field of `Loan` except `{closed, drawn, repaid}` is identical at every future observation once the loan is created. VARIABLE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: `Loan` struct NatSpec — "Every field is immutable once stored" except the three mutable servicing fields. Sources: ST-07.
- [x] **GL-30** `ovrfloToken.owner() == address(vault)` for the campaign's whole life. VALID_STATE, SHOULD-HOLD, LOW. Evidence: the vault is set as owner at deploy and never transfers ownership. Sources: ST-18.
- [x] **GL-31** **[GL-70 successor — mandatory]** For a closed loan `L`, `loan.drawn` equals `ghost_loanStreamWithdrawnAtClose[L] − ghost_loanStreamWithdrawnAtCreation[L]`, computed using ONLY the close-time snapshot recorded the moment `L` closed — NEVER a live re-read of `sablier.getWithdrawnAmount`. The property must branch on `loan.closed` alone, and BOTH closure paths (`close` and a full `repay`) must record the close-time snapshot, since both return the stream and enable re-pledging. VARIABLE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: `docs/solutions/logic-errors/stream-reuse-after-loan-close-property-fix.md` — the pre-rewrite predecessor of this property (also numbered GL-70) produced a REAL false positive: after `closeLoan` returns the stream NFT, the borrower can re-pledge it to a new loan; `getWithdrawnAmount` is cumulative across ALL uses of a stream, so a live read attributes the new loan's draws to the old, already-closed loan. The fix was exactly this close-time snapshot discipline. Sources: ADV-10 (constructed directly per synthesis hard requirement, not merged from another candidate).

## Specific Properties

### Round-Trip & Rounding

- [x] **SP-01** `supply` → `withdraw` with no intervening borrow refunds exactly the amount supplied, with `epoch.filled` unchanged. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: `amount` is forced UNIT-aligned by construction (`NotUnitAligned` guard); `_toWei(_toUnits(x)) == x` must hold for escrowed amounts or GL-02/GL-03 break. Sources: RT-01, ST-24. Called after: `roundTrip_supplyWithdraw` (new handler).
- [x] **SP-02** **[Pattern C2, non-mergeable]** N repeated supply/withdraw cycles never drift the actor's underlying balance. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: no supply- or withdraw-side fee exists, so N repetitions of an exact identity stay exact — catches accumulation bugs a single round trip masks (e.g. an off-by-one in `filledHistory` that only manifests after repeated leaf mutation). Sources: RT-02. Called after: `roundTrip_supplyWithdraw` (new handler, called repeatedly across the stateful campaign).
- [x] **SP-03** N repeated wrap/unwrap cycles never drift the actor's underlying balance. HIGH_LEVEL, SHOULD-HOLD, MEDIUM. Evidence: no arithmetic at all in `wrap`/`unwrap` (OVRFLO.sol:312-340); lower bug-likelihood than SP-02 but the cheapest regression guard against a future fee/rounding addition. Sources: RT-03. Called after: `roundTrip_wrapUnwrap` (new handler).
- [x] **SP-04** `previewDeposit`'s reported split is exactly what `deposit` actually applies in the same block. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: both call `_approvedRate → _computeSplit` with identical pure math and no intervening mutation. Sources: RT-04. Called after: `ovrflo_deposit`.
- [x] **SP-05** A fresh, fully-vested loan can always be closed: `close` never reverts `NotCovered` once the stream's withdrawable reaches full deposit. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: I-20 (`obligation ≤ remaining`) ∘ E-4, derived from `StreamPricing.sol:52-59`'s documented floor/ceil discipline — the *behavioral* consequence of the central rounding invariant; if `grossPrice`'s floor and `obligation`'s ceil drift apart, this catches it as a permanently-open loan rather than only a numeric mismatch. Sources: RT-05. Called after: `lending_close_clamped` with `advanceTime=true`.
- [x] **SP-06** `targetBorrow == type(uint128).max` (the documented max-borrow sentinel) partial-fills instead of causing an arithmetic panic. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: OVRFLOLending.sol:1070 inline comment — `_toUnits(type(uint128).max)` would overflow `SafeCast.toUint64`, which the inlined `/ UNIT` avoids; this is the ONE documented deliberate exception to the conversion discipline, and a future "cleanup" reusing `_toUnits` would silently reintroduce the revert. Sources: RT-06. Called after: `lending_borrow` with `targetBorrow = type(uint128).max`.
- [x] **SP-07** `obligation ≤ remaining` at origination, checked black-box against Sablier state observed immediately before the borrow (not by reimplementing the pricing formula). VALID_STATE, SHOULD-HOLD, HIGH. Evidence: the numeric twin of SP-05, but fires on every borrow rather than only on fills reaching a full-vest close, localizing a violation to the exact fill that caused it. Sources: RD-01. Called after: `lending_borrow`.
- [x] **SP-08** **[reachability caveat]** When `actualBorrow` lands exactly on `grossPrice`, `obligation == remaining` EXACTLY, not merely `≤`. Needs a deterministically constructed scenario (a seed setting apr/ttm so the accrual factor divides evenly) — with `UNIT = 1e12`, hitting this boundary exactly is a low-probability event under random fuzzing. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: StreamPricing.sol:129-133 NatSpec — the fast path exists to avoid "any floor/ceil mismatch at the boundary"; a flip of either rounding direction is invisible under the general `≤` check but shows up here. Sources: RD-02. Called after: `scenario_exactFillBoundary` (new deterministic handler).
- [x] **SP-09** **[gating caveat]** Once a loan is closed AND every overlapping position has zero remaining claimable (`allDrained`, checked — not assumed), the residual `proceeds[loanId]` pot is at most 1 wei per contributing position. **Only sound gated on `allDrained`** — checking `proceeds ≤ contributors` while a known contributor still has unclaimed entitlement false-positives, since that entitlement is legitimately unclaimed value, not stranded dust. A `loansOf(positionId, 0, 50)` scan bound may miss overlaps when more than 50 loans per position share an epoch — widen `maxN` or paginate if that bound is hit. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: I-21; OVRFLOLending.sol:220-223 "dust is lender-unfavorable and strands here by design" (plan risk #5) — this is the plan-mandated bound, not a bug report. Sources: RD-03. Called after: `lending_claim` (opportunistic drain-check).
- [x] **SP-10** `previewStream`/`previewDeposit`'s reported split matches exactly what `deposit` actually applies. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: the vault-side analogue of the lending market's view/money-path identity; the only preview surface in `src/`. A divergence means a frontend simulation misrepresents what a user gets. Sources: SPEC-03. Called after: `ovrflo_deposit`.
- [x] **SP-11** `repay`'s outstanding decreases by precisely the repaid amount with no time-dependent discount, regardless of how early the repayment lands relative to `seriesMaturity`. VALID_STATE, SHOULD-HOLD, MEDIUM. Evidence: repayment is at face by design — an early repayment hands lenders their promised fixed amount sooner, never a discounted one; worth exercising across a wide range of `block.timestamp` since a generic delta-pair check would state the bare arithmetic identity and miss the timing-irrelevance point. Sources: SPEC-04. Called after: `lending_repay_clamped`, fuzzed across `handler_skipTime`.

### Structural Postconditions

- [x] **SP-12** `supply` allocates exactly one position id with stored fields matching the call inputs, and appends exactly one `lenderPositionAt` entry at the pre-call `lenderPositionCount` index. STATE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: single write path (OVRFLOLending.sol:392-404). Sources: ST-01, ST-02. Called after: `lending_supply`.
- [x] **SP-13** `withdraw` mutates only that position's leaf plus its tree ancestors (no sibling leaf moves, no struct-field changes); a second `withdraw` with no intervening borrow always reverts `NothingToWithdraw` (no double refund). STATE_TRANSITION, SHOULD-HOLD, MEDIUM. Evidence: `setLeaf` touches only the ancestor path by construction; the `unfilled == 0` check guards the double-refund case. Sources: ST-03, ST-04. Called after: `lending_withdraw`.
- [x] **SP-14** `borrow` allocates one loan id; `loanAt[market][aprBps][epoch][seq]` is newly populated at the pre-call `loanCount`; exactly one `borrowerLoanAt` entry is appended. STATE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: single write path (OVRFLOLending.sol:472-490). Sources: ST-05, ST-06. Called after: `lending_borrow`.
- [x] **SP-15** `close` on an `outstanding == 0`, not-yet-closed loan: sets `closed = true`, draws nothing (`drawn` unchanged), still returns the stream. STATE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: targets the documented legal reachable state (reachable via a prior full-harvest through `claim` without ever closing); a mutation removing the `if (outstanding > 0)` guard would double-count `drawn` or call `sablier.withdraw(..., 0)`. Sources: ST-10. Called after: `lending_close`.
- [x] **SP-16** `repay` adds exactly `amount` to `loan.repaid`; a full repay (`remaining == 0`) latches `closed = true` AND returns the stream, both in the same call. STATE_TRANSITION, SHOULD-HOLD, HIGH. Evidence: OVRFLOLending.sol:580-587. Sources: ST-11. Called after: `lending_repay`.
- [x] **SP-17** TickTree structural correctness: `append` returns a permanently unique, never-reused leaf index; `setLeaf` touches only the ancestor path; `fillStart` equals the pre-call `filled` and post-call `filled` equals `fillEnd`. STATE_TRANSITION, SHOULD-HOLD, MEDIUM. Evidence: TickTree.append/_replaceLeaf; OVRFLOLending.sol:1067,1084,1088. Sources: ST-12, ST-14, ST-15. Called after: `lending_supply`, `lending_borrow` (needs the TickTree harness getters — see property-plan.md).
- [x] **SP-18** A `supply` by actor A never touches another lender's `lenderPositionAt` index or any other lender's `Position` struct. STATE_TRANSITION, SHOULD-HOLD, LOW. Evidence: per-lender-keyed mapping writes only. Sources: ST-22. Called after: `lending_supply`.
- [x] **SP-19** `borrow` mutates NO `Position` struct at all — the architectural claim the blind-fill design rests on: fill gas is flat in positions crossed *specifically because* no position is written. STATE_TRANSITION, SHOULD-HOLD, LOW. Evidence: `_fillTick` never reads or writes `positions[...]`, only `Epoch` storage. Sources: ST-23. Called after: `lending_borrow`.

### Lazy Attribution & Claim Correctness

- [x] **SP-20** For any loan, the sum of `contributionOf(loanId, positionId)` over every position on that loan's exact `(market, aprBps, epoch)` tape equals `fillEnd − fillStart`. HIGH_LEVEL, SHOULD-HOLD, HIGH. Evidence: E-1, following from I-1 (tiling) + I-2 (frozen history) + X-2 — flagged by the x-ray as "the load-bearing property of the whole v1-lite design." Sources: SPEC-07. Called after: `lending_claim` (expensive — run at reduced frequency or in `afterInvariant`).
- [x] **SP-21** `claim` on a position with zero tape overlap with the loan (including a numerically-identical interval from a DIFFERENT epoch) always reverts (`NoOverlap`/`EpochMismatch`), never pays out. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: `_overlapUnits` checks tape identity (market/aprBps/epoch) BEFORE interval arithmetic, specifically because "leaf numbering restarts per epoch, so intervals from different epochs can collide numerically" — the tape-equality check, not the interval arithmetic, is what blocks a cross-epoch claim. Sources: ADV-02. Called after: `lending_claim` (constructed non-overlapping pair, try/catch).
- [x] **SP-22** No claim ordering across positions overlapping the same loan lets any one claimer collect more than its pro-rata share of what has actually been recovered — even on an over-vested stream, claiming first grants no unfair advantage. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: `claim`'s `harvestCap = min(withdrawableAmountOf(stream), outstanding)` is explicitly called out in NatSpec as "a security invariant, not arithmetic detail — on an over-vested stream, bare `withdrawable` would let the first claimer drain value belonging to co-lenders." Sources: ADV-03. Called after: `lending_claim`.
- [x] **SP-23** A successful `borrow`'s net proceeds (`actualBorrow − feeAmount`) is always `≥` the caller's own stated `minAcceptable` floor. VALID_STATE, SHOULD-HOLD, HIGH. Evidence: `if (outcome.actualBorrow - outcome.feeAmount < minAcceptable) revert BelowMinAcceptable();`, unconditional and checked before any state mutation or external call — the borrower's only slippage protection against a tick thinner than expected at execution time. Sources: ADV-07. Called after: `lending_borrow`.
- [x] **SP-24** A griefer who withdraws a position immediately before another actor's `borrow` lands can, at worst, cause that `borrow` to revert (`EmptyTick`/`BelowMinimum`) on a thinned tick — it cannot cause the victim to lose funds or leave partial state, only gas. VALID_STATE, EXPLORATORY, MEDIUM. Evidence: none cited — inferred from EVM revert-reverts-all-state-changes semantics, not a documented guarantee specific to this contract. Sources: ADV-08. Called after: `lending_borrow` (try/catch, balance-unchanged check on revert).
